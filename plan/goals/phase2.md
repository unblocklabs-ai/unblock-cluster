/goal Complete Phase 2 ("Embedding runs") of `plan/build_plan.md`. That document remains the authoritative spec — treat its "Pipeline Design → Embedding run", "Storage Schema" (embedding_vectors, embedding_items), "Graph Config" (embedding section), and "Phase 2" sections as binding. Build on the Phase 0/1 code; the run executor, records store, and config validation already exist.

Desired end state: an embedding run can be created over REST, embeds a graph's records through a provider behind agent-settable throughput controls, persists content-addressed L2-normalized vectors, reports live progress, reuses every unchanged vector on re-runs (zero provider calls), and is cancellable between batches — all verified by a green pytest suite using the mock provider, plus an opt-in real-API integration test.

Deliverables:

1. Embedding text rendering in `datagraph/core/embedding_text.py`: given a record and the graph's `embedding` config, render the text to embed. With `textTemplate` set, substitute `{field}` placeholders (absent/null fields render empty). Without it, emit the plan's stable labeled-lines format — one `field: value` line per configured `textFields` entry, skipping absent/null fields, `tags` joined with ", ". Truncate the rendered text to `maxInputTokens` tokens using tiktoken's `cl100k_base` encoding. `text_hash` = sha256 of the final (post-truncation) text.
2. Provider layer in `datagraph/core/openai_client.py`: an async provider interface (`embed_batch(texts) -> list of float32 vectors`) with two implementations — the existing mock (moved/adapted to fit; deterministic, no network, honors `dimensions`) and a real OpenAI provider using the official SDK's AsyncOpenAI with `max_retries=0` (OUR layer owns retries — no double-retry stacking). Our retry policy: exponential backoff with jitter on 429/5xx/timeouts, honoring the SDK's advertised retry-after when present, bounded attempts, then fail the run with a clear `error_text`. Config validation now accepts `embedding.provider` values `"openai"` and `"mock"`; README documents `"mock"` as a deterministic test/dev provider whose vectors are semantically meaningless.
3. Token-aware batch packing: batches of at most 512 inputs AND at most 200,000 total tokens per request (compute with tiktoken; both caps configurable constants). A single over-long text is already truncated by (1), so every text fits some batch.
4. Throughput controls, per run: `requestsPerMinute` implemented as a token-bucket rate limiter and `maxConcurrency` as a semaphore over in-flight provider requests. Both must be injectable/fakeable for tests (inject a clock or sleep function — throttle tests must not sleep real wall-time to pass).
5. The `embed` run type, registered as an IO run on the existing executor: `POST /api/graphs/:gid/embeddings` with an optional body of embedding-config overrides (any `embedding.*` key, merged onto the graph config and re-validated; echoed into `params_json`) → returns the created run; poll/cancel via the existing generic runs API. Execution: snapshot the graph's records at run start; render texts and hashes; create one `embedding_items` row per record; diff hashes against `embedding_vectors` for (model, dimensions) — hits are marked reused instantly with no provider call; misses are packed, dispatched through throttle+concurrency, L2-normalized, stored as float32 blobs, committed per batch. Progress: `progress_json` = `{"embedded": n, "reused": n, "total": n}` updated as batches land. Stats on completion: records, unique texts, reused count, provider requests made, model, dimensions. Cancellation between batches: already-persisted vectors stay, run ends `cancelled`.
6. `datagraph/core/vectors.py`: pack/unpack float32 vector blobs and L2-normalize — the read path Phase 3 will build on.
7. Empty-graph and no-op edge cases: embedding a graph with 0 records succeeds immediately with total 0; a second identical run reports 100% reused with zero provider calls.

# Phase 4 `/goal` prompt (for gpt-5.5 / Codex)

/goal Complete Phase 4 ("LLM labeling") of `plan/build_plan.md`. That document remains the authoritative spec — treat its "Pipeline Design → Label run", "Storage Schema" (cluster_labels), "Graph Config" (labeling section), and "Phase 4" sections as binding; the default prompt text is the supplement-DTC prompt in `plan/initial_draft.md` ("Suggested default prompt"), used verbatim. Build on Phases 0–3.

Desired end state: a cluster run's topics can be labeled by `gpt-5.4-mini` through an async `label` run — one structured-output chat call per non-noise cluster over its stored representatives — with labels persisted per (cluster run, cluster), merged into the topics APIs, relabelable per topic, and resilient to per-cluster failures; all verified offline with a scripted chat provider plus an opt-in real-API test.

Deliverables:

1. Chat provider layer alongside the embedding provider in `datagraph/core/openai_client.py` (or a sibling module): an async interface `label_cluster(prompt, representatives) -> LabelResult` where `LabelResult` is `{label: str, summary: str, keySignals: [str], tags: [str], coherent: bool}`. Real implementation: AsyncOpenAI with `max_retries=0` (our existing retry/backoff owns retries), model from config, STRUCTURED OUTPUT via the SDK's JSON-schema support (strict schema matching LabelResult). If the model returns output that fails schema/JSON validation, retry once, then treat as a per-cluster failure. The provider must be injectable via a factory seam on the executor, exactly like `embedding_provider_factory`.
2. Prompt assembly: system/base prompt = `labeling.prompt` when non-empty, else the built-in default (verbatim from `plan/initial_draft.md`, stored as a module constant). Representative payload: the topic's stored representatives (up to `labeling.topK`, default 12), each rendered as a stable block — sourceType, title when present, customerText — truncated to ~700 characters per record. `prompt_hash` = sha256 of the effective base prompt. Unit-test the assembly: topK respected, truncation applied, absent titles skipped, stable format.
3. The `label` run type, IO kind, registered on the executor: `POST /api/graphs/:gid/views/:vid/label` with optional body `{clusterRunId?, clusterIds?, labeling?: {...overrides}}` (overrides merged onto graph config and re-validated). Resolution at POST time: cluster run defaults to the view's `default_cluster_run_id`; none → 409 naming the cluster endpoint. `clusterIds` (list of ints) limits the run to those clusters — this IS the topic-relabel API; omitted → all non-noise clusters. Execution: fetch each target cluster's summary + representative records; up to 4 concurrent provider calls with the existing retry/backoff; persist one `cluster_labels` row per successfully labeled cluster (id, label_run_id, cluster_run_id, cluster_id, model, prompt_hash, top_k, label, summary, key_signals_json, tags_json, coherent, created_at). Progress: `{"labeled": n, "failed": n, "total": n}` as calls complete. Failure policy: a cluster that exhausts retries is recorded in stats `failedClusterIds` and does NOT fail the run; the run fails only if every target cluster fails (or a setup error occurs). Stats: targets, labeled, failed, failedClusterIds, providerRequests, model, promptHash. Cancellation between provider calls; already-persisted labels stay. On success (≥1 labeled): set the view's `default_label_run_id`.
4. Labels merged into reads: `GET .../topics`, `GET .../topics/:tid` — each topic's `label` field becomes an object `{label, summary, keySignals, tags, coherent, labelRunId, model}` from the NEWEST `cluster_labels` row for that (resolved cluster run, cluster id), or null when none exists. Relabeling a topic therefore supersedes older rows without deleting them (history stays in the table).
5. Offline-vs-real split, same pattern as Phases 2–3: CI tests use a scripted provider injected through the factory seam (returns configurable/deterministic LabelResults, can be programmed to fail specific clusters or return invalid-schema output); one opt-in integration test SKIPPED unless `OPENAI_API_KEY` is set that builds a small graph (structured mock embeddings → cluster offline), real-labels 2–3 clusters with `gpt-5.4-mini`, and asserts each label is a non-empty string of ≤ 10 words with a non-empty summary. The plan's "synthetic topics get recognizable labels / junk cluster yields coherent: false" checks join the deferred real-key manual acceptance (extend `scripts/quality_eval.py` with a labeling step behind the same key gate).

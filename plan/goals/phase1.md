# Phase 1 `/goal` prompt (for gpt-5.5 / Codex)

/goal Complete Phase 1 ("Graphs, records, views") of `plan/build_plan.md`. That document remains the authoritative spec — treat its "Graph Config", "Storage Schema", "API Surface", "Rulings on the Draft's Open Questions" (#3 timestamps, #6 validation), and "Phase 1" sections as binding. Build on the existing Phase 0 scaffold (`datagraph/` package, migration runner, run executor); do not rework Phase 0 code except where this phase requires it.

Desired end state: graphs, records, and views are fully CRUD-able over REST with strict validation; the synthetic 5k dataset uploads cleanly in batches and upserts idempotently; invalid records produce precise per-record errors; scoped views return provably correct record counts — all verified by a green pytest suite.

Deliverables:

1. Graph API: `POST /api/graphs` (name + config → graph, plus an auto-created `all_records` view with empty scope), `GET /api/graphs`, `GET /api/graphs/:gid` (config, record count, views summary), `PATCH /api/graphs/:gid` (partial config: top-level sections replace wholesale, merged result re-validated as a whole), `DELETE /api/graphs/:gid` (cascades via existing FKs). Config validation implements the plan's "Graph Config" section exactly: `embedding.textFields` is REQUIRED at creation (non-empty list of strings); `cluster.space.method` accepts only `"umap"` or `"none"` (422 otherwise); unknown keys anywhere in the config are rejected (nothing is accepted-and-ignored); all documented defaults are filled in and returned.
2. Records API: `POST /api/graphs/:gid/records` accepting `{"records": [...], "onInvalid": "reject"|"skip"}` with at most 1000 records per request (422 above). Default `"reject"` is atomic: any invalid record fails the whole batch with a per-record error report. `"skip"` upserts the valid subset and returns the rejects. Upsert key is `(graph_id, recordId)` — re-uploading updates the row and `updated_at`, never duplicates. Response reports `created`, `updated`, and (for skip) `rejected` with reasons. Also `GET /api/graphs/:gid/records` (paged: `limit` default 100 max 1000, `offset`; stable order `timestamp_ms ASC, id ASC`; returns total; filters: `sourceType`, `product`, `sentiment`, `start`/`end` time range) and `GET /api/graphs/:gid/records/:rid` (accepts either the internal `rec_…` id or the agent's recordId).
3. Record validation per ruling #6: required — `recordId`, `sourceType`, `sourceName`, `sourceRecordId`, `customerText` (non-empty after trim), `timestamp`. Optional — `title`, `recordUrl`, `product`, `sku`, `rating` (number), `sentiment`, `tags` (list of strings), `metadata` (open object). Two constraints learned from the Phase 0 generator: explicit `null` must be treated identically to an absent key for every optional field, and `sourceType` is an OPEN vocabulary — do not hardcode an enum. Unknown top-level keys on a record are rejected (agents use `metadata` for custom fields). The full submitted record is stored in `normalized_json`.
4. Timestamp parsing per ruling #3: ISO 8601 strings only. Offset-aware values convert to UTC; naive values are interpreted as UTC; numbers (epoch) and non-ISO strings are rejected with a clear message. Persist both `timestamp_utc` (canonical ISO, `Z` suffix) and `timestamp_ms`.
5. Views API: `POST /api/graphs/:gid/views` (`{name, description?, scope}`), `GET /api/graphs/:gid/views`, `GET /api/graphs/:gid/views/:vid`, `GET /api/graphs/:gid/views/:vid/records` (same pagination/shape as graph records). View names unique per graph (409 on conflict). List/detail responses include the (currently null) default run id fields and a live-computed `recordCount` for the view's scope.
6. Scope language compiled to SQL exactly per the plan's API Surface section: `sourceTypes[]`, `sourceNames[]`, `products[]`, `skus[]`, `sentiments[]`, `ratings {min,max}`, `timeRange {start,end}` (against `timestamp_ms`), `tagsAny[]`, `metadataEquals {key: value}`. Empty scope `{}` means all records. Unknown scope keys → 422. Implement as a single reusable scope-to-SQL module (`datagraph/core/` is fine) — later phases reuse it for cluster runs.
7. Error shape: validation failures return a consistent JSON structure — for batch uploads, one entry per bad record: `{index, recordId (when parseable), errors: [{field, message}]}`. Precise and actionable; an agent must be able to fix its payload from the message alone.

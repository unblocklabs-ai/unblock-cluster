/goal Complete Phase 8 ("Pilot fixes: run promotion, mismatch warnings, response casing, agent filtering guidance") of `plan/build_plan.md`. The binding spec is that document's Amendment 2026-07-03 (c) — read it first; it records what the first real-data pilot found and exactly what this phase changes. Build on the shipped Phases 0–7.

Desired end state: tuning runs no longer silently hijack a view's defaults (`setDefault` param); artifact and topics responses warn explicitly when their resolved runs mismatch instead of silently dropping labels/trends; run responses use camelCase like every other API surface; embed stats expose retry counts; and the README's agent contract teaches pre-upload filtering and the cheap iterate-on-quality loop — all verified by a green suite.

Deliverables:

1. `setDefault` request param (boolean, default `true`; non-boolean → 422; echoed in `params_json`) on all four view-scoped run POSTs — cluster, layout, label, trends. When `false`, the run executes and persists all outputs normally but skips EVERY view-default update it would otherwise make (cluster: `default_cluster_run_id` + `default_embedding_run_id`; layout: `default_layout_run_id` + the fill-if-unset embedding ref; label: `default_label_run_id`; trend: `default_trend_run_id`). This is the tuning workflow: experiment with `setDefault: false`, promote by re-running the winner with `true` (re-runs are cheap — clustering reuses embeddings). Document the workflow in the README.
2. Mismatch warnings — no more silent degradation. `GET .../artifact` and `GET .../topics` (list and single-topic) gain a `warnings: [...]` array (always present, empty when healthy) with deterministic, actionable strings for: (a) the resolved cluster run has no `cluster_labels` rows — name the label endpoint; (b) the view's `default_label_run_id` labels a DIFFERENT cluster run than the one resolved — say which; (c) the view's `default_trend_run_id` exists but its cluster run mismatches, so trend snapshots are absent. This is the complement of `setDefault`: even when someone does repoint defaults, the API says what broke instead of returning quietly label-less topics (the pilot lost an hour to exactly that).
3. Run-response casing normalized to camelCase: `RunResponse` becomes `id, graphId, viewId, type, status, params, progress, errorText, inputRefs, stats, createdAt, startedAt, completedAt`. This is the API's only snake_case surface and a direct pilot DX complaint. Update every internal consumer — tests, `scripts/demo_seed.py`, `scripts/quality_eval.py`, README examples. Breaking change is acceptable (pre-1.0, single known consumer, called out in the final summary and PR).
4. Embed run stats gain `providerRetries`: total retry attempts beyond first tries across all batches (0 on a clean run). `embed_with_retry` already tracks attempts; surface the sum. The pilot could not tell whether retries happened.
5. README agent-contract additions (this is a first-class deliverable, not doc polish — the pilot showed ~41% of an unfiltered real graph is junk):
   - A "Pre-Upload Filtering" subsection carrying the plan's exclusion list into the agent contract: exclude outbound-only/company-authored messages (OOO and autoresponders), transactional and automated campaign sends (newsletters, tracking-pixel/URL-dominant bodies), vendor/PR outreach, records with zero customer-authored messages (use inbound-message counts when the source has them), and records with no meaningful free text (e.g. score-only NPS rows). Frame the service-side signals that reveal leftover junk AFTER upload: junk-labeled topics, `coherent: false`, and the outliers endpoint.
   - An "Iterating On Quality" subsection: upload → cluster → label → review topics/coherence/outliers → tighten filters → delete graph (or re-upload) → repeat, with the explicit point that content-addressed embeddings make re-runs nearly free — only changed texts are re-embedded.
   - The `setDefault` tuning workflow from deliverable 1.

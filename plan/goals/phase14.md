/goal Complete Phase 14 ("Summarization runs") of `plan/build_plan.md`. Build on the shipped Phases 0–13. No new dependencies.

Desired end state: a graph's records can be summarized by an optional `summarize` run — one `gpt-5.4-nano` structured-extraction call per record against a SERVICE-OWNED strict schema — and embedding runs can embed the summary representation instead of raw text, making a raw-vs-summary A/B two runs on one graph; junk is gated semantically at the embed boundary; extracted fields become facets; representatives and evidence always remain raw customer text — all verified offline with a scripted summarizer plus an opt-in real-API test.

Deliverables:

1. New `summarization` config section (validated like the others, all keys echoed with defaults): `{provider: "openai", model: "gpt-5.4-nano", context: null, requestsPerMinute: 500, maxConcurrency: 4, prompt: null}`. `context` is an optional agent-supplied string (≤ 4,000 chars, 422 beyond) of static brand/service background — e.g. what the company sells and what real support traffic looks like — injected into the summarizer's system prompt so junk judgment ("is this spam for THIS business?") is informed. `prompt` overrides the built-in instruction text entirely (same pattern as labeling). The EFFECTIVE prompt = (override or built-in) + context block; `promptHash` = sha256 of the effective prompt — so changing context or prompt correctly invalidates cached summaries.
2. The built-in summarizer prompt (module constant, crafted with care — this is product surface): instructs structured extraction of the PRIMARY customer issue; explicitly IGNORE out-of-office notices, auto-replies, and system-generated messages that appear INSIDE otherwise-legitimate multi-message threads; QUOTE the customer's key phrases verbatim (the anti-homogenization guardrail — the bible's evidence that customer vocabulary matters); classify the whole record's `junkType`.
3. Strict output schema, service-owned, validated like `LabelResult` (retry once on invalid, then per-record failure): `{issue: str, product: str|null, desiredResolution: str|null, sentiment: str|null, keyCustomerPhrases: [str], junkType: "none"|"ooo"|"vendor_pitch"|"newsletter"|"platform_notification"|"other_non_support"}`.
4. The `summarize` run type (IO kind; the label-run execution pattern: provider-factory seam for tests, up to 4 concurrent calls via config, existing retry/backoff, providerRetries in stats, progress `{summarized, reused, failed, total}`, per-record failure isolation with `failedRecordIds` capped in stats, cancellation between calls, `setDefault` not applicable). Content-addressed exactly like embeddings: a `record_summaries` store keyed `(model, prompt_hash, text_hash)` holding the validated JSON + a rendered summary text (stable labeled-lines including the verbatim quotes); text_hash = the record's rendered RAW embedding text hash, so re-runs and incrementals reuse summaries for unchanged records with ZERO provider calls (assert this in tests). Schema change is expected here — add the table + any run bookkeeping via the established migration approach and say so in the summary. `POST /api/graphs/:gid/summarize` with optional `summarization.*` overrides (merged + revalidated, echoed in params).
5. Summary representation for embeddings: embedding-run requests gain `representation: "raw" (default) | "summary"`. With `"summary"`: resolution at POST time requires a succeeded summarize run covering the graph (409 naming the summarize endpoint otherwise; records without summaries are counted `missingSummaries` and skipped); the embedded text is the rendered summary; junk gating — records with `junkType != "none"` are EXCLUDED by default (`includeJunk: false`, overridable) so downstream cluster populations are semantically filtered; `input_refs` gains `summarizeRunId`; the content-addressed embedding cache just works because the rendered summary is the text being hashed. Cluster/layout/label/trend runs need NO changes — they already intersect on embedding coverage.
6. `facetBy` gains `summary.<key>` for `issue`, `product`, `desiredResolution`, `sentiment`, `junkType`: resolved through the run-refs chain (topics' cluster run → embedding run → summarizeRunId); 422 with an actionable message when the resolved chain has no summarize lineage. Same `(none)`/top-20/`(other)` semantics as existing facets.
7. Receipts principle, enforced and tested: representatives, topic records, evidence payloads, and the artifact continue to carry RAW `customerText` — never summary text — regardless of representation. Summaries are derived artifacts; expose them only via a summarize-run read (e.g. `GET /api/graphs/:gid/summarize-runs/:runId/report` returning junk counts by type + per-record junkType listing for the agent's drop/keep decisions) and optionally alongside single-record reads.
8. README: a "Summarize-Then-Embed (Optional)" section — when to use it, the A/B workflow (two embedding runs + two cluster runs on ONE graph, canonical questions, watch for suspiciously merged topics = homogenization), the `context` field with an example, cost/latency expectations (per-record LLM calls; content-addressing amortizes re-runs), and the receipts principle. UPDATE THE PRIVACY SECTION: summarization is a third customer-text flow to OpenAI alongside embeddings and labeling — state it plainly.
